## Root cause 1: the supply chain is broken between discovery and acquisition

**Evidence.** In 24 hours the acquire worker never received a manifest job. Every run it logged `queue_empty_after_replenishment / needs_acquisition_or_promotion`. Over the same period discovery returned 6,041 links. The four extract workers have only one claimable catalogue between them.

**Why it caps output.** Capacity is not the constraint. The factory has had nothing new to process. Running more workers, OCR or parser passes cannot add identities or edges until new catalogues are promoted into acquisition.

**Fix (DB side, needs Supabase access).**
1. Find the promotion step from discovered links to `master_catalogues`. Candidates are the cron controller, a source-approval gate (`sources.access_state`), or the allowlist.
2. Make promotion automatic for allowlisted hosts whose robots policy passes. Rank by expected yield: dedicated supersession and cross-reference lists first, broad retail catalogues last.
3. Add a monitor that alerts when the acquire queue is empty for 2 consecutive runs while discovery is returning links.

**Related risk.** The dispatcher (`rv-runner-capacity.yml`) never re-dispatches after a non-successful matrix. It prints "Any retry requires atomic outage reservation…", but no such retry path exists. One failed job therefore stops the factory until a human dispatches it by hand. That is fail-closed with no recovery. It needs a bounded automatic retry (for example, at most 2 retries with a 30-minute cooldown, using the existing `retry_eligible`).

## Root cause 2: the control plane re-does work instead of advancing it

**Evidence.**
- One catalogue was re-claimed in 37 of 39 runs.
- Reimo was processed about 3.5 times in a day.
- 42 Reimo batches were held because the database assigned an adapter name the deployed worker did not know. The database and the worker had drifted apart.
- More than 40 `rv-*` pg_cron jobs exist, but the repo contains **one** migration and no gateway function source.
- There are two different circuit-breaker modules (`runner_circuit_breaker.py`, which is used, and `engineering/runner_allocation_circuit_breaker_v1.py`, which is orphaned).
- The repo is two days old (49 commits on 20–21 Nov), yet the database holds 20,131 parts and 3,456 completed batches. The code that produced most of the data is not in this repository.

**Why it caps output.** "Complete" does not mean "advanced". A batch can finish, be reset by a controller, and be claimed again, using a worker slot every cycle. With the logic outside Git, nobody can review the controllers or roll them back.

**Fix (needs Supabase access).**
1. Export every `rv_private` function, view and cron command into versioned migrations, as a baseline only with no behaviour change. This is the rollback point.
2. Map which cron jobs write `master_catalogue_batches.state`, then remove duplicate controllers one at a time, each behind a feature flag.
3. Make batch completion idempotent per `(catalogue_id, sha256, page_start, extractor_version)`. A batch is re-queued only when the extractor version changes and a benchmark shows gain.
4. Have the gateway reject unknown adapters at **claim time**, and add a CI contract test so the worker's adapter list is checked against the database.

## Root cause 3: the relationship extractor cannot read how catalogues print relationships

**Evidence (code).**
- `explicit_replacement_rows`, `replacement_sentence_rows` and `distributor_oem_rows` use `re.fullmatch` on a single PDF text line. Any extra word on the line ("12345 Seal kit – replaced by 67890") loses the edge.
- `replacement_table_rows` only accepts tables with **exactly two columns**.
- `relationship_rows` marks a whole page as qualified if *kit*, *only*, *if*, *note*, *serial* or `*` appears anywhere on it. Nearly every spare-parts page contains one of these, and the code comments say auto-verification only applies to unflagged pages.
- No rule reads reverse wording ("B replaces A", "B ersetzt A"), stacked "Old/New part number" labels, or distributor cards where the article number and the manufacturer number are on different lines.

**Evidence (benchmark).** Both extractors were run on identical pages. "current" replays the exact production path: `adaptive_page` → `relationship_rows` → `catalogue_relationship_extractor`.

| Set | Extractor | Recall | Clean precision | False positives |
| --- | --- | --- | --- | --- |
| Dev (19 cases, 20 gold edges) | current production | 0.30 | 1.00 | 0 |
| Dev | relationship_graph_v2 | 1.00 | 1.00 | 0 |
| Held-out (12 cases, 8 gold edges, written after v2 was frozen) | current production | 0.00 | 0.00 | 1 |
| Held-out | relationship_graph_v2 | 0.62 | 1.00 | 0 |

The production false positive came from "12345 and 12346 replaced by 67890 kit": production asserted 12346 → 67890. v2 misses three held-out cases, all conservatively: a "Replaced by:" line below the part line, a part number with a footnote asterisk, and a sentence with two candidate subjects. They are recorded and deliberately left unfixed so the held-out set stays honest.

**Caveat.** These are synthetic pages reproducing real layout patterns. They show which layouts each extractor *can represent*, not real-world recall. The mandate's ≥98% precision gate has to be measured on hand-annotated real pages. The tooling for that is in place (below).

**Also found: silent identity drops.** `publish_generic_master_identities` only publishes rows whose `extraction_method='labelled-column-v1'` and whose position ends in `colN`. `labelled_card_rows` and `explicit_inline_rows` label their rows `labelled-column-v1` without `colN`, and `hwh-code-v1` is not in the adapter list. Those identities are staged and then never published, and nothing reports it. Query F in the diagnostics file quantifies it.

## What I built (branch `claude/relationship-benchmark-v1`, commit `b0d4818`, not pushed)

- `scripts/relationship_graph_v2.py`: typed `supersedes` (direction kept), `oem_xref` (marked as a distributor assertion, never manufacturer authority) and `fits` (a scope claim, never interchangeability). It reads tables with any number of columns and remarks/description columns, statements anywhere in a line in either direction, stacked labels and multi-line cards. Each statement carries its own qualifiers, and date or serial scope is kept as an attribute. **Staging only**: no publication path, and no interchangeability edge type exists.
- **Shadow mode** in `rv_master_disk.py`: v2 runs in the same page traversal, and each batch logs a `relationship_v2_shadow` line with v1 and v2 counts and the differences. Nothing is sent to the gateway, and shadow errors are caught, so batch outcomes cannot change. This is covered by the worker self-test.
- `benchmarks/`: the dev set, the held-out set, a runner that replays production, and `real_page_shadow.py`, a read-only comparison on a real PDF. It uses the production allowlist, robots and same-origin redirect policy, checks SHA-256, and writes a disagreement list for annotators.
- `.github/workflows/relationship-benchmark.yml`: CI gates on every extractor change, plus a manual run against any allowlisted PDF. It defaults to the Reimo 2025 PDF with its expected SHA-256, takes 40 sampled pages, has no OIDC and no database access, and uploads an artifact.
- `supabase/diagnostics/2026-11-22_baseline_readonly.sql`: read-only queries for the baseline and the three root causes.
- All 34 existing and new tests pass, and the worker `--self-test` passes.
